# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

NUTRANTARA is a web-based learning game for high-school Biology (Grade XI, digestive system), built for Project Based Learning. A 3D multiplayer adventure (Three.js) with a teacher control panel. It runs on a classroom Node server, or as single-player from static hosting. All UI text, comments, and docs are in **Indonesian**. Keep new user-facing text and comments in Indonesian.

Requirements and scope come from `Desain_Game_NUTRANTARA.docx.md` (main design reference) and `Paket_Persiapan_Pengembangan_NUTRANTARA.docx.md`. `MEMORY.md` in the repo root logs the scope decisions: single-player → 0.3 multiplayer + teacher panel → 0.4 3D → 0.5 floating archipelago with accounts, lobby, map select, drop-in, and in-world missions → 0.6 bright "Nusantara Ceria" theme with Indonesian cultural props → 0.7 one-answer grading with post results and a report screen → 0.8 open world: six free-exploration islands, minimap, and sprint → 0.9 each post is its own open-world region of ±1000 × 650 m ("100 × 65 km" in the game's story) on a 32400×15200 map → 1.0 project teams (PjBL) of 1–4 players with rotating roles, shared team missions, and team voting → 1.1 block terrain (biomes, valleys, mountains, swimmable water, block structures) in the six post regions and per-island rotating weather. Read it before changing scope. If the user changes scope, discuss the implications for platform, student data, operations, and cost before implementing. The game must stay original: genre inspiration is fine, copying characters, levels, or the look of an existing game is not.

## Commands

```bash
npm install          # ws (runtime) + three (dev, only used to refresh vendor/)
npm start            # classroom server on :3000 — prints player URL, /admin URL, and admin PIN
npm test             # test/smoke.js: spawns server.js on port 3999 with a temp data dir, drives accounts/2 players/admin over WebSocket
npm run vendor       # copy three.module.min.js from node_modules into vendor/three/
for f in *.js test/*.js; do node --check "$f"; done   # syntax check (what CI runs)
```

There is no build step, bundler, or linter. `npm test` is the only test: one script with sequential `ok(cond, label)` assertions. To test a single behaviour, add or edit assertions there. There is no per-test runner.

Env vars: `PORT`, `NUTRANTARA_ADMIN_PIN` (random each start if unset; **required** when `NODE_ENV=production`, otherwise the server exits), `NUTRANTARA_MAX_PLAYERS` (60), `NUTRANTARA_DATA_DIR` (`data/`), `TRUST_PROXY=1` (use X-Forwarded-For for rate limiting). CI (`.github/workflows/blank.yml`) runs the syntax check, `npm test`, and a Docker build plus a `/health` check. For deployment (Docker, Render), see `docs/DEPLOY.md`.

## Architecture

**No build, plain browser scripts plus ES modules.** `play.html` loads classic `defer` scripts that publish globals, followed by ES modules that read those globals:

- Classic: `missions.js` → `window.NUTRANTARA_MISSIONS`, `world-data.js` → `window.NUTRANTARA_WORLD`, `net.js` → `window.NutraNet`, `game.js` → `window.NutraGame`, `world.js` → `window.NutraWorld2D`, `map-art.js` (the "Peta" screen: positions the post pins that `game.js` renders over the illustration `assets/peta-nusantara*.webp`, and handles the route state, lock clouds, zoom, parallax, and Nara's speech bubble; it watches `#map-nodes` with a MutationObserver).
- Modules: `world3d.js` (→ `window.NutraWorld3D`, sets `NUTRA_WORLD_MODE`), `app.js` (app flow: login/register → lobby → island select → world; guest offline mode with no server), which import `characters.js`, `quest.js` (in-world terminals, report boards, seal altars, and the post-result card), `fx.js`, `absorb.js` (Post 3: the Gerbang Pilah card sorter for digestion vs absorption and the Simulator Vili 3D, a self-contained mini Three.js scene inside the panel that disposes itself when the panel closes; stored in `posts[3].activity.sort`/`.villi`), `lab.js` (Post 2's Meja Uji Reagen: virtual food-test lab with Lugol/Benedict/Biuret/Sudan III/microscope, an evidence-gated accusation, and ★ ratings; stored in `posts[2].activity.lab`), `region.js` (fills each post region: village hub, paths to every mission object and bridge, climbable terrace hills, ponds, cultural camps, kites, 3 extra archive shards per post, and per-biome block-style InstancedMesh vegetation placed on the terrain; it passes every feature to `terrain.addRegion` so they stay flat), `terrain.js` (block terrain, see below), `weather.js` (per-island climate: weathers rotate every 8 minutes from `Date.now`, so all players agree without the server; fog/sky/light blends plus rain, frost, ash, leaves, dust, gentle lightning, and a rainbow; atmosphere only, no movement penalty; lightning off and particles reduced under `prefers-reduced-motion`), `culture.js` (procedural Indonesian cultural props: candi bentar, meru, penjor, stupa, rumah gadang, gunungan, gong, ondel-ondel, kites, pinisi, local foods), and `vendor/three/three.module.min.js`.
- Styles: `styles.css` (base), `app.css` (app flow and world HUD), `landing.css`, `admin.css`, and `theme.css` loaded last on every page (the bright theme: kawung/tumpal patterns, Baloo 2 headings, teal-and-gold buttons). Put new visual styling in `theme.css`.
- Controls in the 3D world use a dual-input scheme (camera and movement are separate). Movement: WASD relative to the camera; ←/→ turn the facing direction, ↑/↓ move along it; Shift runs; a left click on the ground walks there; while standing, the cursor sets the facing direction; a gold ground arrow shows it. Camera: hold right/middle mouse (or left-drag) to rotate; the wheel zooms (`ZOOM_MIN`–`ZOOM_MAX`); V toggles free mouse-look (pointer lock, Esc exits); Q locks the camera onto the mission object nearest the view direction within `LOCK_RANGE` (cyan hexagon ring; with no target it resets); C resets the camera behind the player; R/F (or PageUp/PageDown) look up/down. Tab is deliberately not used for lock-on, because it is the keyboard focus key. Gamepad (standard mapping, `pollGamepad`): left stick moves, right stick camera, A jump, X interact, B/L3 hold run, R3 lock-on, Y reset, D-pad ↑/↓ zoom, Back minimap. Touch: the left joystick moves, swiping the canvas rotates, pinch zooms, BIDIK = lock-on. M enlarges the minimap. Lock and reset logic live in `updateCamControl`; manual camera rotation (`lookBy`) releases the lock.
- Camera modes (`CAM_MODES` in `world3d.js`, chosen with K, gamepad D-pad ←/→, or the KAMERA bar above GRAFIS; saved in `localStorage` `nutrantara-cam`; each mode keeps its own pitch/zoom in `camMem`): `orbit` (third-person, free 360°, the default), `bahu` (over-the-shoulder: close, the player faces the view and strafes), `iso` (isometric/top-down: high camera with a narrow FOV; R/F tilt to top-down; left-drag/one finger/right stick pans `camCtl.pan`, which drifts back once the player walks; a lock centres between the player and the target instead of rotating), `fp` (first person: camera at `EYE_H`, own body and facing arrow hidden, zoom = FOV). `updateCamera` positions the camera per mode; the frame loop sets the FOV (`camFov`) and, in `iso`, pushes the fog out (`isoView`).
- `index.html` + `landing.js` is the landing page. It opens behind a loading screen (`#splash` + `splash.js`, a classic script loaded synchronously right after the markup so it paints before the heavy modules): the user's illustration `assets/layar-muat*.webp` is shown whole (contain, with a blurred fill), and a transparent button, progress bar, and effect layers (portal ripples, title sweep, glints, Nara's eye glow, blinking lids, chest light, speech bubble) sit on top in percentages of the 1672×941 artwork, over the parts drawn in it ("MULAI GAME", title, portal, Nara). Re-cropping or replacing the image means re-measuring those percentages in `theme.css` (the pixel coordinates are listed in its comment). Every load plays a 3-second interactive intro (`INTRO` 2.4 s + `OUTRO` 0.6 s in `splash.js`, wall-clock time that pauses only while the tab is hidden): the art settles in, the bar fills, then the view zooms into the portal and the home page opens. The pointer drives parallax and a particle canvas (`#splash-motes`), clicks/taps spark, and Nara reacts when touched; MULAI GAME/Enter/Space/Esc enters early. If the page has not fired `load` by 2.4 s, the bar holds at 95% (15 s cap). With `prefers-reduced-motion` it is a static 3 s screen. Without JS it stays `hidden`. Its #peta section is `peta3d.js`: a procedural, realistic 3D floating-archipelago diorama built from `world-data.js` (noise terrain, stratified cliffs, lakes, waterfalls, instanced forests, a cloud sea, light bridges, gold post portals, DOM "POS n" pins); the old SVG map stays as the fallback. `admin.html` + `admin.js` is the teacher panel.

**Shared data between browser and server.** `server.js` loads `missions.js` and `world-data.js` through `vm` with a fake `window` (`loadBrowserScript`). `test/smoke.js` does the same. These two files must stay plain scripts that only assign to `window.*`: no `import`/`export`, no DOM access. `missions.js` holds the challenge content **and the answer keys** (types: `single`, `multi`, `order`, `sort`).

**Scoring lives in two places that must agree.** Since 0.7 each challenge is answered **once** (`gradeChallenge` in `game.js`, used by both `submitAnswer` for the in-world board and the DOM mission screen): correct = 30 points, wrong = 0 points but the challenge still counts as complete, and the student moves on after seeing the correct answer and the explanation (the mission's `success` text). Seal +20; maximum 420. A post can be sealed once every challenge is answered (right or wrong) and the reason has `MIN_REASON` characters. The server re-validates the stored progress in `validateProgress` in `server.js`: it recomputes `correct` from the answer keys with `isCorrect` (it ignores the client's `correct` flag), sets points, and flags only invalid states, such as a seal with unanswered challenges or a challenge marked complete without a response (⚠ in the admin panel). Evaluation lives in `game.js` (`evaluatePost`, `evaluateAll`, `renderReport`): grades A ≥90%, B ≥75%, C ≥60%, otherwise D. The interim report grades only the posts already started. If you change scoring or challenge types, update both, plus the smoke test. Known limitation: the answer keys ship to the client. Post 1 has 100 case variants and Post 2 has 4 (broken amilase/protease/lipase/empedu; the variant's `activity.caseId` also drives the lab) (`m.variants`, generated deterministically at the end of `missions.js`; variant 0 is the original). The student's variant lives in `posts[1].variant`: `applyVariants` in `game.js` copies it onto the mission object on every `saveState`, and `challengesFor` in `server.js` grades with that variant's keys. Do not change the generator's seed or lists, or saved progress will point to different cases.

**Server (`server.js`, single file, no framework).**
- Static files come from an explicit `STATIC` whitelist map. **New front-end files must be added there**, or they will 404 on the classroom server even though they work from `file://` or static hosting. The CSP is strict (`script-src 'self'`), so no inline scripts and no CDNs; Three.js is vendored for this reason and for offline LAN use.
- HTTP API: `/api/register`, `/api/login`, `/api/logout`, `/api/me`, `/api/status`, `/health` (also reports `storage`: whether the data folder is writable; checked at startup by `checkStorage` and on every save). The Docker image starts as root only to `chown` the data folder (a Render disk can be mounted root-owned), then runs the server as `node` via `su-exec`; CI tests this with a root-owned bind mount. Passwords use scrypt and auth is rate-limited per IP.
- WebSocket `/ws`: JSON messages keyed by `type`. Players send `join`, `move`, `progress`, `chat`, `zone`, `spawn` (with `to: playerId` it drops the player next to a squadmate), `emote`, `party` (`create`/`join`/`leave`: "Regu proyek" project teams with a 6-character invite code, also accepted as the link `play.html?regu=CODE`; persisted in `db.teams`, max 4 members, wrong codes rate-limited), `team-op` (small `{p, set}`/`{p, push}` operations on the team's shared post data plus a contribution note), `team-vote` (a proposal or vote for a Papan Laporan answer), and `ping`. The admin sends `admin-auth`, then `admin` with a sub-command (`set-paused`, `set-movement`, `set-posts`, `teleport`, `kick`, `reset-password`, `export`, …) and `admin-refresh`. The client side of the protocol lives in `net.js`, which emits events (`welcome`, `progress-sync`, `settings`, `reset`, …) that `game.js` subscribes to with `net.on`.
- Persistence: a single JSON file, `data/classroom.json` (gitignored), holding settings, players, teams, and chat.

**Project teams (PjBL, since 1.0).** Students form teams of 1–4 freely; members may play at different times. Per post, the team owns the shared part (`SHARED_KEYS` in `server.js` = `TEAM_KEYS` in `game.js`: `variant`, `evidence`, `activity`, `challenges`, `started`; for Post 6 also `initial`, `review`, `revision`, `reached`). Reasons, reflections, and seals stay individual, so a student's score = team challenge points + their own seals (max still 420). The server is authoritative: `overlayTeam` copies the team data into a member's progress before `validateProgress`. Clients never send whole team state: `game.js` diffs the shared fields against the last server copy on every `saveState` and sends `team-op` operations (`push` only for primitive items or objects with an `at` timestamp); `challenges` cannot be set by ops. A team answer locks when 2 members propose the same response, or 1 if no other member was active in the last 24 h (`handleTeamVote`). Roles: `NUTRANTARA_TEAM` at the end of `missions.js` defines 4 roles per post and a task → role map; `team.js` (classic, `window.NutraTeam`) assigns role r at post p to member `(r + p − 1) mod n`, gates tasks (a task owned by an online teammate is refused; an offline holder's task can be taken over and is logged), and draws the team HUD. Gates are called from `quest.js`, `lab.js`, `absorb.js`, and the Dapur Juara step saves in `game.js`. Without a server or team everything is solo and ungated.

**Offline / fallback behaviour is a feature.** With no server, `net.js` reports it cannot connect and the game runs single-player, saving to `localStorage` (`nutrantara-save-v2:<user>` in `game.js`). Without WebGL, the game falls back to the 2D canvas world (`world.js`). World coordinates are a logical 32400×15200 map, 1 unit = 0.1 m in 3D (`world-data.js`: post regions 1–6 in a 3×2 grid, each an ellipse of 5000×3250 units; plaza island 0 at the junction of posts 1/2/3/6; `kind: 'wild'` exploration islands 7–12 in the gaps; bridges from big regions start at the nearest edge point), shared by the 2D world (which shows a 960×600 window that follows the player), the 3D world, the admin live map, and server teleport/spawn. Use `W.isPost(id)` rather than `id > 0` to detect a post. Mission objects in `quest.js` are placed relative to the region centre but capped to a ±220×140 m core (`sx`/`sz`); the rest of the region is free exploration. The 3D camera uses a close view range while playing (fog 110–330 m, far 800) and a far one in the map-select overview (`setView`); the compact minimap shows a ±320 m window around the player, M shows the whole map. Wild islands have no missions, are always in `allowedIslands`, and are reachable only by bridges whose other end is open. Their props, climbable platforms, and extra archive shards are defined in `LANDMARKS[7–12]` in `world3d.js`. New shards must be appended at the end of the list, because shard ids are list indexes stored in localStorage (order: plaza/post spots, wild-island shards, then region shards from `region.js`).

**Block terrain (since 1.1, `terrain.js`).** Each post region is a grid of 2 × 2 m columns with 1 m steps, one biome per post (`BIOMES`: 1 hutan, 2 lembah, 3 gunung, 4 rawa, 5 gumuk, 6 kaldera). Heights are computed once per region at load, deterministically from a per-post seed. Every feature from `region.js` (hub, station, mission objects, bridge ends, camps, terrace hills, ponds) and the path corridors are locked flat at height 0. Natural terrain changes by at most 1 block per column (a two-pass min-plus distance transform), and its height or depth may only grow with Manhattan distance from locked cells, so there are no trap pits. Only structures (towers with spiral stairs and a penjor, candi, mesas with a ramp, boulders) have walls of 2+ blocks. If you change the generator, re-check these invariants and reachability. Meshes are built per 64 m chunk around the player (radius 360 m on 3D Tinggi, 250 m on 3D Ringan) and disposed when far; the play fog is capped at that radius. The flat region disc (`regionTops`) shows only in the map overview, and the region's sand and cliff cylinders are open-ended so lakes and valleys are not covered. In `world3d.js`, `groundAt` = max(terrain, `SWIM_Y` −1 m): deeper water is swum at 60% speed. Moving into a column is allowed if its ground is ≤ feet + 1.05 m (an automatic step; a jump climbs 2 blocks), stepping down snaps, and the camera is pushed above the terrain. `move.h` (0–8 m on the server) is now the height above the terrain block, and other players are drawn at terrain + h, so the server is unchanged. The six tower-top archive shards are appended after all existing shards. `quests.nearest` receives the height above ground.

**Save schema:** if you change the shape of the `game.js` state, bump `SCHEMA_VERSION` (old saves are discarded when the version does not match).

## Constraints from the design docs

- Students use aliases, never full names. Chat is readable by the teacher.
- All numbers in Posts 1–5 are simulated data, not nutrition advice.
- Accessibility targets: keyboard (Tab/Enter), state never shown by color alone, 1024 px width, 125% zoom, touch, low-end laptops (the "3D Ringan" / 2D graphics options), and `prefers-reduced-motion` (respected in `fx.js`).
